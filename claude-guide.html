Part 1

Claude 생태계 이해

Claude는 단일 제품이 아닌 모델 + 제품군의 패밀리다. 개발자가 어디서 무엇을 쓸지 결정할 때 필요한 지도.

범용 — 모든 개발자
Chapter 01

왜 지금 Claude를 알아야 하는가

"Anthropic 내부에서 코드의 대다수는 이제 Claude Code가 작성한다. 엔지니어는 아키텍처·제품 사고·여러 에이전트의 동시 오케스트레이션에 집중한다."Anthropic — Claude Code product page

소프트웨어 엔지니어링은 두 종류의 일로 나뉜다. 결정론적인 일 — 같은 입력에 같은 출력이 나와야 하는, 컴파일러·DB·결제 시스템의 영역. 그리고 판단이 끼어드는 일 — 자유 텍스트 분류, 요청 해석, 초안 작성, 코드 작성처럼 사람이 해 오던 영역.

LLM은 두 번째 영역에서 갑작스럽게 강력해졌다. 코드 작성은 그 영역의 정점이었고, 그래서 가장 큰 변화가 일어나는 곳이기도 하다. Claude Code는 Anthropic이 그 변화를 직접 도구로 만든 결과물이다.

이 가이드가 다루는 것 / 다루지 않는 것

다룸

Claude Code(터미널/IDE), Claude Desktop App, Cowork, MCP 커넥터를 사용해 ERP를 개발·운영하는 워크플로우. 프롬프트 작성법, 컨텍스트 관리, 에이전트 패턴.

다루지 않음

Anthropic API/SDK 직접 호출 코드, API 키 관리, 자체 에이전트 구현. 이 가이드의 대상은 소비자로서의 개발자지 LLM 인프라 제공자가 아니다.

ERP 개발자의 일에서 LLM이 잘하는 것

  • 코드 작성·리팩터링·디버깅 — Claude Code가 가장 잘하는 일
  • 비정형 입력의 정형화 — 자유 텍스트를 구조화 데이터로
  • 분류·라우팅 — 들어온 요청을 카테고리·우선순위별로
  • 긴 문서 요약·질의 — 사내 규정·계약서·매뉴얼에서 답 찾기
  • 초안 생성 — 견적·답변·릴리즈노트의 1차 드래프트

LLM에게 시키면 안 되는 것

  • 정확한 산술 계산 — 부가세, 단가, 잔액. 항상 결정론적 코드로.
  • 최신 사실 단독 답변 — 학습 시점 이후의 가격·재고는 모른다. 도구로 외부화.
  • 완전 자율 결정 — 환각이 0이 될 수 없으므로 영향 큰 작업에는 검증 게이트가 필요.
  • 결정론적 출력 — 같은 입력에도 미묘하게 다른 답. 절대적 일관성이 필요한 곳에 부적합.

이 가이드의 학습 동선

Part 1~3은 도구를 떠나서도 유효한 보편 개념이다. Part 4~5는 Claude Code를 본격 도구로 익힌다. Part 6~7은 그것을 ERP 도메인(가상 회사 AcmeERP)에 적용한다.

이미 Claude Code를 어느 정도 써본 개발자라면 Part 4를 빠르게 훑고 Part 5부터 읽어도 된다. Part 1~3은 챗 인터페이스에서 프롬프트를 쓸 때나 Cowork에서 작업을 지시할 때도 그대로 쓸모 있다.

Chapter 02

모델 패밀리와 제품군

"각 표면(surface)은 같은 Claude Code 엔진을 공유한다. CLAUDE.md, 설정, MCP 서버는 모두에서 동일하게 작동한다."Anthropic — Claude Code overview

모델 패밀리 — 2026년 5월 기준

모델강점이 가이드에서
Claude Opus 4.7가장 강력한 추론·에이전틱 코딩, 장시간 작업복잡한 리팩터링, Plan Mode 기획, Cowork 자율 실행
Claude Sonnet 4.6지능과 속도의 균형, 가장 많이 쓰는 일꾼일상 코딩, 빠른 버그 수정, 자동 메모리 작업
Claude Haiku 4.5빠르고 가볍고 저렴간단한 코드 변환, 부속 작업 빠른 실행

Claude Code는 작업 성격에 따라 모델을 자동 선택하기도 한다(예: opusplan 모드는 Plan 단계만 Opus로). 사용자가 직접 선택할 수도 있다.

제품군 — 개발자가 알아야 할 6가지

① Claude.ai — 채팅 인터페이스

웹/모바일 채팅. 빠른 프롬프트 검증, 동료에게 공유할 수 있는 산출물 생성, 일상적 질의응답. 코드 작업이 본격화되기 전 "프로토타이핑 출발선"이다.

② Claude Code — 이 가이드의 주역

터미널·IDE(VS Code/JetBrains)·데스크톱 앱·웹에서 동작하는 에이전틱 코딩 도구. 코드베이스를 읽고, 파일을 편집하고, 명령을 실행하고, 테스트를 돌리고, 커밋·PR까지 한다. 개발자가 일하는 환경 안에서 작동한다.

③ Claude Desktop App

macOS/Windows 데스크톱 앱. Claude.ai의 채팅에 더해 Cowork 모드를 켤 수 있다. MCP 커넥터(Google Drive, Slack, Jira 등)도 데스크톱 앱에서 가장 풍부하게 다룰 수 있다.

④ Cowork — 데스크톱에서 자율 작업

Claude Desktop App의 모드 중 하나. 로컬 파일 시스템에 권한을 주고 Claude가 자율적으로 다단계 업무를 수행한다 — 폴더 정리, 보고서 작성, 스프레드시트 생성 등. 비개발자도 쓸 수 있게 만들어졌지만, ERP 개발자에게도 문서 자동화·정기 작업에 유용하다. Part 7에서 다룬다.

⑤ MCP — Model Context Protocol

Claude(또는 다른 LLM)가 외부 시스템에 접속할 때 쓰는 표준 프로토콜. Claude Code, Claude Desktop, Cowork 모두 같은 MCP 커넥터를 공유한다. 한 번 연결하면 어디서든 쓸 수 있다. Chapter 6과 12에서 깊이 다룬다.

⑥ Claude in Chrome (베타)

크롬 확장 프로그램. 브라우저 안에서 Claude가 페이지를 보고, 폼을 채우고, 작업을 수행한다. 웹 기반 ERP나 사내 시스템 자동화에 쓰일 수 있다. 이 가이드의 메인 포커스는 아니다.

이 가이드의 무게 중심

개발자에게 가장 중요한 표면은 Claude Code다. 일하는 환경(터미널·IDE) 안에서 작동하고, 코드베이스 전체를 이해하며, 결과물(파일·커밋·PR)이 그대로 검증 가능한 형태로 남는다.

Cowork는 코드 바깥의 일 — 보고서 작성, 스프레드시트 생성, 폴더 정리, 정기적 문서 처리 — 에 적합하다. 개발자에게는 보조 도구지만, ERP 운영 업무 일부는 여기서 자연스럽게 자동화된다.

"하나만 고르라면 Claude Code"가 이 가이드의 입장이다. 코드 작업의 ROI가 가장 크고, 거기서 익힌 패턴(CLAUDE.md, MCP, Plan Mode)이 다른 표면에도 그대로 적용되기 때문이다.

Chapter 03

핵심 6원칙

"Claude 4.x 모델은 명확하고 명시적인 지시에 잘 반응한다. 원하는 출력을 구체적으로 적을수록 결과가 좋아진다."Anthropic — Claude 4 Best Practices

프롬프트 엔지니어링은 신비한 기예가 아니다. 사람을 가르치듯 맥락을 주고, 예시를 보이고, 형식을 못박는 것이다. 다음 6가지가 거의 모든 케이스에 적용된다 — 채팅이든 Claude Code든 Cowork든.

① 명확하고 구체적인 지시

나쁜 예 (Claude Code)

"이 버그 좀 고쳐줘"

좋은 예 (Claude Code)

"OrderService.CalculateTotal에서 부가세 라인이 두 번 합산되는 버그가 있다. 단위 테스트를 먼저 추가해 버그를 재현하고, 수정한 뒤, 테스트가 통과하는지 확인해줘."

② 컨텍스트와 "왜"를 함께

Claude 4.x는 이유를 함께 들으면 명시되지 않은 엣지케이스에서도 원칙을 일반화한다.

# 나쁜 예
"발주 라인 모델에 created_at 필드를 추가해줘."

# 좋은 예 — 이유까지
"발주 라인 모델에 created_at 필드를 추가해줘. 우리는 감사 로그
요구사항 때문에 모든 트랜잭션 시점을 추적해야 한다. 기존 데이터
마이그레이션 스크립트도 함께 만들어줘 — 기존 행은 발주 헤더의
created_at을 상속하면 된다."

③ 예시 보여주기 (Few-shot)

예시는 설명을 백 마디 하는 것보다 강하다. 특히 출력 형식·코드 스타일을 잡을 때.

# Claude Code에서 — 새 컨트롤러를 만들 때
"새 VendorController를 만들어줘. 우리 코드베이스의 기존 컨트롤러
스타일을 따라야 한다. 참고할 예시:
- src/Controllers/CustomerController.cs (CRUD 패턴)
- src/Controllers/OrderController.cs (DTO 변환 패턴)
이 두 파일을 먼저 읽고 같은 패턴을 적용해줘."

④ XML 태그로 구조화

프롬프트가 길어지면 XML 태그로 영역을 명확히 구분한다. 코드 작업뿐 아니라 분류·추출 작업에서도 유용하다.

<role>당신은 신중한 코드 리뷰어다.</role>

<rules>
- 보안 이슈는 무조건 우선 지적한다.
- 스타일 이슈는 critical_only=false일 때만 언급한다.
- 추측은 하지 마라 — 증거 없으면 의견을 보류한다.
</rules>

<diff>
{이 PR의 diff}
</diff>

<output_format>
{ "issues": [{ "severity", "file", "line", "description" }] }
</output_format>

⑤ Role / 페르소나

한 문장이라도 모델에게 누구인 척 하라고 알려주면 출력의 톤·정확도가 달라진다.

"당신은 보수적이고 신중한 시니어 .NET 엔지니어다.
의심스러우면 변경하기 전에 질문하고, 검증된 패턴만 사용해라."

Claude Code의 CLAUDE.md(Chapter 9)는 이 페르소나를 프로젝트 단위로 영구히 지정하는 방법이다.

⑥ 출력 형식 명시

프로그램 통합에서 가장 중요한 원칙. 출력은 항상 코드가 파싱할 수 있는 형식이어야 한다.

Claude Code 사용 시에도 응용된다 — "결과를 JSON 파일 analysis.json으로 저장해줘"처럼 구체화하면 Code가 그 파일을 만들고 다음 작업에 그대로 쓸 수 있다.

Chapter 04

고급 기법

"한 프롬프트에 다 욱여넣지 마라. 단계가 다른 일은 단계로 나누면 일관성이 크게 올라간다."Anthropic — Prompting Best Practices, paraphrased

Chain of Thought — 단계별 사고

복잡한 추론(다단계 분석, 인과 추적)에서 "단계별로 생각하고 답해라"를 명시하면 정확도가 오른다. 더 강력한 변형은 Extended Thinking — Claude가 별도 사고 영역에서 충분히 추론하고 답을 내는 모드다.

Claude Code에서는 "think hard" / "think harder" / "ultrathink" 같은 키워드로 사고 예산을 더 늘릴 수 있다. 어려운 디버깅이나 아키텍처 결정 시 유용하다.

Prompt Chaining — 작업 분할

한 작업이 여러 단계로 나뉜다면 각자의 프롬프트로 분리해서 결과를 다음 단계 입력으로 넘긴다.

이건 단지 좋은 습관이 아니라 Anthropic이 권장하는 Claude Code의 정식 워크플로우다. Part 4의 Plan Mode가 이 흐름을 도구 차원에서 지원한다.

Long Context — 큰 입력 다루기

PDF 50장, 코드베이스 전체, 표준 문서 통째로 — 큰 컨텍스트를 다룰 때:

  1. 긴 문서를 위에, 질의는 아래에 — 모델은 마지막에 본 질문 기준으로 응답을 구성한다.
  2. "먼저 관련 부분을 인용한 뒤, 답해라" — 그라운딩 강제. 환각이 줄어든다.

Claude Code는 큰 코드베이스에서 자동으로 관련 파일만 골라 읽기 때문에 직접 long context 관리를 신경 쓸 일은 적다. 하지만 긴 사양서 분석·계약서 검토 등에서는 위 두 원칙이 그대로 작동한다.

Plan Then Execute — Claude Code의 황금 패턴

실무에서 가장 많이 쓰는 패턴

① 계획만 만들게 한다 — "구현하지 말고 변경 계획만 적어줘."
② 사람이 검토한다 — 빠진 것, 잘못 이해한 것을 수정 노트로 남긴다.
③ "노트 반영해, 아직 구현은 하지 마" — 한 번 더 정제.
④ 합의된 후에야 구현 시작.

Anthropic 권장 워크플로우의 핵심이며, 한 시간의 사전 투자가 6~10시간의 구현 손실을 막는다고 보고된다. "don't implement yet"이 핵심 가드 문구다.

Chapter 05

환각 최소화

"근거가 없으면 거짓말을 하느니 모른다고 답하라 — 라고 명시하라. 그리고 근거가 어디 있는지 인용하게 하라."Anthropic — Prompting Best Practices, paraphrased

환각은 LLM의 본질적 한계다. 100% 제거는 불가능하지만, 다섯 패턴으로 실용적 수준까지 줄일 수 있다. 코드 작업이든 비즈니스 문서 작업이든 동일하게 적용된다.

패턴 1 — "모르면 모른다고 해라" 명시

가장 단순하지만 가장 효과적이다. CLAUDE.md나 시스템 프롬프트에 "근거가 없으면 답을 만들어내지 말고 질문하라"라고 적어 둔다.

# 좋은 CLAUDE.md 한 줄
"확신이 없는 결정·날짜·숫자·승인은 만들어내지 마라.
필요하면 사용자에게 질문하거나 'unknown'으로 표시해라."

패턴 2 — 근거 인용 강제

Claude Code에서 매우 효과적이다. "이 함수가 어떻게 동작하는지 설명할 때, 직접 본 코드 라인 번호를 함께 인용해라" — 환각이 눈에 띄게 줄어든다.

패턴 3 — 숫자는 LLM에게 시키지 마라

원칙적인 규칙. 합계, 비율, 평균 같은 산술은 결정론적 함수가 한다. LLM은 어떤 항목을 더할지 결정만 하고, 더하기 자체는 코드가 한다.

위험

"이 거래 데이터의 월별 합계를 계산해줘."
→ 직접 산술 → 가끔 틀림

안전

"이 거래들을 월별로 분류하는 SQL을 짜줘. 합산은 SQL이 한다."
→ 결정론적 결과

패턴 4 — 외부 사실은 도구로

"지금 X의 값이 얼마야?"라는 질문에 LLM이 답하게 두지 말고, 적절한 도구(MCP나 Bash)를 호출하게 시킨다. Claude Code는 이미 Bash, 파일 읽기, 웹 검색 등의 도구를 기본 제공한다.

패턴 5 — 출력 검증 게이트

LLM 출력을 그대로 다음 단계에 넘기지 마라. 항상 (a) 형식 검증 (b) 비즈니스 룰 검증 (c) 위험도 높은 작업이면 사람 승인 — 세 단계.

Claude Code에서는 이 검증을 훅(hooks)으로 자동화할 수 있다 — 파일 편집 후 자동 린트, 커밋 전 테스트 실행 등(Chapter 13).

AcmeERP 사례 — 거래처 매핑의 환각

Claude Code로 거래처 마이그레이션 스크립트를 만들 때, "거래처 코드가 비어 있으면 비슷한 이름으로 추정해서 채워줘"라고 시키면 코드가 환각한다.

해결: "코드는 절대 추측하지 마라. 비어 있으면 needs_review 플래그를 두고, 사람이 확인할 큐로 넘긴다." LLM의 역할은 "비정형 → 정형의 추출"까지, "정형 → 진실의 매핑"은 코드의 일이다.

Tool Use & MCP — 개념

"Claude는 도구를 호출하지 않는다 — 호출하기로 결정할 뿐이다. 실제 호출은 도구 측 코드가 한다."Anthropic — Tool Use Overview, paraphrased

Tool Use 사이클

중요한 통찰: LLM은 직접 파일을 읽지 않는다. "Read 도구를 이렇게 부르고 싶다"고 결정만 한다. 실제 읽기는 Claude Code 측에서 일어나고, 결과가 LLM에게 다시 전달된다.

MCP — 도구의 표준 어댑터

Model Context Protocol은 Claude(또는 다른 LLM 클라이언트)가 외부 시스템에 접속할 때 쓰는 표준 프로토콜이다. 비유: "AI 도구의 USB-C".

왜 표준인가? 같은 외부 시스템(예: Jira)을 (a) Claude Code (b) Claude Desktop App (c) Cowork — 세 곳에서 다 쓰고 싶다면, 어댑터를 한 번만 만들면 된다. MCP 서버 하나에 클라이언트 셋이 붙는다.

이미 만들어진 MCP 커넥터

Anthropic과 커뮤니티가 제공하는 MCP 커넥터가 이미 풍부하다. 개발자가 자주 쓰는 것:

  • GitHub — 이슈·PR·코드 검색
  • Google Drive / Workspace — 문서 조회·편집
  • Slack — 메시지 검색·발송
  • Jira / Linear — 티켓 관리
  • PostgreSQL / SQL — DB 쿼리
  • Filesystem — 로컬 파일 자율 접근
  • Notion / Confluence — 위키·문서

개발자가 자체 MCP 서버를 만드는 것도 가능하지만, 일단은 기존 커넥터를 조립하는 것이 출발점이다. 자체 MCP 서버 구축은 사내 ERP를 노출하고 싶을 때나 의미 있다.

이 가이드는 MCP 서버를 직접 만들지 않는다. 기존 커넥터를 Claude Code/Desktop에 등록·사용하는 워크플로우만 다룬다(Chapter 12).

Chapter 07

하네스 사고법

"하네스 설계는 프론티어 에이전틱 코딩의 성능을 좌우하는 핵심이다."Anthropic Engineering Blog

왜 하네스 개념을 알아야 하는가

개발자가 하네스를 직접 만들지 않아도, Claude Code 자체가 정교한 하네스다. 그 안에서 일어나는 일을 이해하면 (a) 왜 가끔 결과가 좋고 가끔 나쁜지, (b) 어떻게 더 일관된 품질을 끌어낼지 보인다.

단일 프롬프트의 함정

Claude Code 없이 단순히 "이 코드 고쳐줘"를 반복하면 자주 무너지는 패턴:

  • 비결정성 — 같은 요청에 매번 미묘하게 다른 결과
  • 자기평가 편향 — "이거 OK?"라고 묻는 순간 모델은 자기 작품을 후하게 본다
  • "좋아 보이는" 출력 — 표면적으론 그럴듯, 실제로는 동작 안 함
  • 긴 작업의 일관성 손실 — 컨텍스트가 차오를수록 초기 지시를 잊음

Anthropic 내부 실험에서 "앱을 한참 만들어 놓고 막상 써보면 핵심 기능이 작동하지 않는" 일이 흔하다고 보고된다. 모델은 똑똑하지만, 똑똑함만으로 일관성이 보장되지 않는다.

하네스 — 모델 주변에 두르는 골격

영단어 harness는 등반·말 장비의 "안전벨트·안장"이다. 하네스는 모델의 능력을 방향 잡고, 측정하고, 제약 거는 외부 구조물이다.

Claude Code가 4영역을 어떻게 채우는가

역할Claude Code의 구현
① GuidesCLAUDE.md, 슬래시 커맨드, 서브에이전트 프롬프트, Plan Mode
② Sensors훅(hooks)으로 자동 린트·테스트, Bash로 검증, 사람 승인 게이트

Generator-Evaluator — 자기평가의 함정

Anthropic의 핵심 발견 중 하나: 모델은 자기 작품을 후하게 본다. 같은 컨텍스트에서 "이거 OK?"라고 물으면 거의 항상 OK라고 답한다.

해법: 평가자를 분리한다. Claude Code의 5가지 워크플로우 패턴 중 Operator 패턴이 이를 구현한다 — 별도의 코드 리뷰어 서브에이전트가 Generator의 결과물을 검토한다.

"과도한 하네스"를 경계하라

Anthropic의 Building Effective Agents 원칙: 가장 단순한 해법을 먼저 시도하고, 필요할 때만 복잡도를 더한다.

실무 권고: 단일 Claude Code 세션 + 명확한 계획만으로도 대부분의 작업이 잘 돌아간다. 서브에이전트, 병렬 워크플로우는 토큰 비용이 3~4배가 되니, 진짜 독립적인 병렬 작업일 때만 꺼낸다.

"가장 큰 실수는 단순한 작업에 에이전트 팀을 동원하는 것이다." 잘 짜인 단일 프롬프트 + Plan Mode가 잘못 조정된 에이전트 팀보다 거의 항상 낫다.

이 단순한 명령에 Claude Code는 자동으로:

  1. README.md나 CLAUDE.md가 있으면 먼저 읽는다.
  2. 주요 디렉토리 구조를 Glob 도구로 훑는다.
  3. 대표 파일 몇 개를 Read로 열어본다.
  4. 그제야 답을 만든다.

이 자동 탐색이 Claude Code의 핵심 가치다. 당신은 컨텍스트를 직접 주입할 필요가 없다. 모델이 도구를 써서 스스로 파악한다.

권한 모드 — 안전 vs 속도

Claude Code는 파일을 수정하거나 명령을 실행하기 전에 기본적으로 사용자 승인을 요청한다. 작업 흐름에 따라 권한 모드를 조정할 수 있다.

  • Default — 모든 변경에 승인 필요. 신뢰 쌓이기 전에는 이 모드가 좋다.
  • Auto-edit — 파일 편집은 자동, 셸 명령은 승인. 익숙해진 프로젝트에서.
  • Plan mode — 변경하지 않고 계획만 작성. 큰 변경을 시작하기 전에.
  • Bypass (실험적) — 모두 자동. 샌드박스나 일회용 환경에서만.

운영 환경(특히 ERP DB·사내 시스템에 닿는 작업)에서는 절대 Bypass를 켜지 말 것. 한 번의 잘못된 명령으로 데이터가 망가질 수 있다. 의심스러우면 Default 모드로.

CLAUDE.md와 메모리

왜 CLAUDE.md가 필요한가

매 세션마다 같은 컨텍스트를 반복해서 설명하지 않기 위해서다. "우리 프로젝트는 .NET 8을 쓰고, ServiceLayer는 EF Core가 아닌 Dapper로 작성하고, 테스트는 xUnit이고..." — 이런 정보를 한 번 적어두면 Claude Code가 자동으로 따라준다.

이건 Part 3에서 본 하네스의 Guides 영역에 정확히 해당한다. 모델이 행동하기 전에 방향을 잡아주는 외부 골격이다.

# AcmeERP — Project Conventions

## What this project is
산업용 부품 유통회사 Acme의 사내 ERP. .NET 8 기반.
거래처 3,000개, 일일 발주 200건, 사내 PDF 500개 누적.

## Tech stack
- Language: C# 12, .NET 8
- ORM: Dapper (EF Core 사용 안 함 — 성능 이슈로 폐기)
- Tests: xUnit + FluentAssertions
- DB: SQL Server 2022
- Logging: Serilog → Seq

## Coding rules
- public API에는 XML doc 주석 필수
- 비동기 메서드는 항상 `Async` 접미사
- DateTime은 항상 UTC로 저장, 표시할 때만 KST
- 통화 계산은 `decimal` 절대 `double`/`float` 금지
- 새 마이그레이션 추가 시 반드시 rollback 스크립트 동반

## Architecture decisions
- 거래처(Vendor) 마스터는 단일 테이블 — 분산 안 함
- 발주는 Header/Lines 분리, Lines는 soft delete
- 인증은 Windows AD + JWT 하이브리드

## Don't
- 거래처 정보는 절대 추측·자동완성하지 마라. 명시되지 않으면 needs_review.
- 외부 API 응답은 항상 5초 timeout. 그 이상은 별도 큐로.
- production DB에 직접 쿼리 실행 금지 — 항상 staging부터.

## Common commands
- 빌드: `dotnet build src/AcmeErp.sln`
- 테스트: `dotnet test --filter Category!=Integration`
- 마이그레이션: `dotnet run --project tools/MigrationRunner`

① 짧게 유지

1500자 이내가 좋다. 길어지면 Claude Code가 핵심 부분을 흘려 읽는다(Backlog.md가 비대해지면 같은 문제 발생이라는 보고가 흔하다). 모든 규칙을 다 적지 말고, 자주 어기는 규칙·잘못 추측하기 쉬운 결정만 적는다.

② "왜"를 짧게 곁들이기

"EF Core 사용 안 함"보다 "EF Core 사용 안 함 — 성능 이슈로 폐기"가 훨씬 강력하다. 모델이 일반화하기 좋다.

③ "Don't" 섹션이 효과적

긍정 규칙보다 부정 규칙(이건 절대 하지 마라)이 환각을 더 잘 막는다. 사람도 마찬가지다.

④ 정기적으로 업데이트

새 규칙이 생기거나 결정이 뒤집히면 즉시 반영. 오래된 CLAUDE.md는 모델을 잘못된 방향으로 끌고 간다. 분기에 한 번 정도는 팀 단위로 검토하면 좋다.

AcmeERP 팀이 도입 후 발견한 것

CLAUDE.md를 도입한 첫 주, 가장 효과적이었던 한 줄: "DateTime은 항상 UTC로 저장, 표시할 때만 KST." 그 전엔 새 코드를 만들 때마다 시간대 처리가 들쭉날쭉했다. 한 줄 추가 후 이 클래스의 회귀 테스트가 처음으로 안정됐다.

자동 메모리 — 사용자가 적지 않아도 학습

Claude Code는 작업하면서 빌드 명령·디버깅 인사이트·반복 패턴을 자동으로 학습한다. 세션을 넘어 보존된다 — 사용자가 따로 적지 않아도.

예를 들어 처음에 "테스트는 어떻게 돌리지?"라고 물었을 때 시행착오를 거쳐 dotnet test --filter ... 명령이 정착됐다면, 다음 세션부터는 같은 질문 없이 그 명령을 쓴다.

자동 메모리는 마법이 아니라 결국 로컬 파일로 저장된다. 위치는 ~/.claude/ 아래의 메모리 디렉토리. 사용자가 직접 들어가서 정리하거나 삭제할 수 있다.

Plan Mode

"가장 신뢰할 만한 운영 워크플로우는 이것이다 — Claude에게 계획만 짜라고 한다(no implementation yet). 에디터에서 검토하고 잘못된 부분을 표시한다. 'address all notes, don't implement yet'으로 돌려보낸다. 모든 결정이 합의되면 그제야 구현을 시작한다."Claude Code best practices, 2026

왜 Plan Mode가 필요한가

한 가지 실험을 가정하자. 어떤 기능을 만드는 데 20개의 결정이 필요하다. Claude가 각 결정을 80% 확률로 맞춘다고 하자. 모든 결정이 동시에 옳을 확률은:

0.820 ≈ 1%

Anthropic 내부 측정에서, 무계획 시도의 성공률이 약 33%에 그쳤다고 보고된다. Plan Mode는 이 20개의 모호한 결정을 한 번 검토된 스펙으로 모아 각각이 거의 100%에 수렴하게 만든다 — 사람이 미리 결정을 내려뒀기 때문이다.

한 시간의 사전 투자가 6~10시간의 구현 손실을 막는다고 보고된다. 큰 기능일수록 효과가 크다.

핵심 가드 문구 — "don't implement yet"

이게 단순한 관용어가 아니다. 이 문구가 없으면 Claude Code는 검토 단계를 건너뛰고 즉시 구현을 시작한다.

매 검토 사이클마다 다음 두 패턴을 반복한다:

  1. "draft a plan, don't implement yet." — 첫 계획 요청
  2. "address all notes, don't implement yet." — 검토 노트 반영
  3. 합의될 때까지 2번을 반복
  4. 마지막에만 "이대로 구현해"

opusplan — 비용·품질의 균형

Opus는 추론력이 좋지만 Sonnet보다 토큰 비용이 높다. opusplan 모드는 자동으로:

  • Plan 단계는 Opus로 (정교한 계획)
  • 실행 단계는 Sonnet으로 (빠르고 저렴)

이 자동 라우팅 덕분에 비용을 의식하지 않고도 비싼 작업과 싼 작업을 자연스럽게 분리할 수 있다.

Plan Mode를 쓰지 말아야 할 때

모든 변경에 Plan Mode를 쓸 필요는 없다. 오버엔지니어링은 그 자체로 비용이다.

Plan Mode가 좋음
  • 여러 파일에 걸친 변경
  • 아키텍처 결정 포함
  • 마이그레이션·DB 변경
  • 외부 시스템 통합
  • "이거 어떻게 할지 잘 모르겠다"
그냥 진행이 나음
  • 오타·작은 버그 수정
  • 1~2 라인 변경
  • 단순 리네임
  • 이미 명확한 작업

경험칙: 변경이 영향 줄 파일이 3개 이상이거나 예상 작업 시간이 30분 이상이면 Plan Mode부터. 그 미만은 직접 진행이 빠르다.

단순 채팅을 넘어, Claude Code가 진짜로 빛나는 곳. 5가지 워크플로우 패턴으로 작업의 성격에 맞는 도구를 고른다. MCP로 외부 시스템을 연결하고, 슬래시 커맨드로 팀이 같은 흐름을 공유한다.

실전 — Claude Code 도구 익히기
Chapter 11

5가지 워크플로우 패턴

"패턴 선택이 결과 양을 결정한다. 4시간짜리 기능 구현이 45분으로 줄어들 수도, 잘못 선택하면 4배 토큰을 써놓고도 더 못 만들 수도 있다."Beyond One-Shot Prompts: 5 Claude Code Workflow Patterns

대부분의 개발자는 Claude Code를 한 가지 방식으로만 쓴다 — 프롬프트 보내고, 답 받고, 반복. 작은 일은 잘 동작하지만 본격 기능 개발에서는 빠르게 한계에 부딪힌다.

Anthropic 공식 가이드와 실무 분석은 5가지 패턴을 정리한다. 같은 도구가 5가지 모드로 동작한다고 보면 된다.

다섯 패턴 한눈에

패턴구조전형적 용도

패턴 ① Sequential — 가장 자주 쓰는 기본형

단일 에이전트가 단계를 순차적으로 실행한다. 표준 형태가 Explore-Plan-Implement-Verify다(그림 2.1).

Sequential — 일상 사이클
> Vendor 마스터에 신용등급 컬럼 추가하는 작업.
  먼저 코드베이스 탐색하고, 계획 짠 뒤, 구현하고, 테스트로 검증해.

[Sequential 패턴 자동 진행]
1. Explore: src/Models, Repositories, Migrations 디렉토리 스캔
2. Plan: 4개 파일 변경 + 마이그레이션 1건 계획 출력
3. Implement: 파일 편집
4. Verify: dotnet test 실행 → 통과 확인

Anthropic 권장 출발선이다. 대부분의 작업이 여기에 속한다. "하나만 골라 시작하라면 이 패턴부터".

패턴 ② Operator — 한 명의 PM, 여러 명의 전문가

중앙 오케스트레이터(operator)가 큰 작업을 쪼개고, 각 조각을 전문 서브에이전트에게 위임한다. 결과를 합쳐 사용자에게 돌려준다.

Claude Code에 복잡한 프롬프트를 주면 이 패턴이 자연스럽게 발동한다. 사용자가 명시적으로 시킬 수도 있다:

    "description": "성능 이슈만 본다",
    "tools": ["Read", "Grep", "Bash"],
    "prompt": "N+1 쿼리, 불필요한 allocation, 동기 차단을 찾아라."
  }
}'

> OrderService.cs를 두 리뷰어에게 모두 보내고 결과를 통합해줘.

사용 시나리오:

  • 코드 리뷰 (보안·성능·스타일을 각자 보고)
  • 리팩터링 (탐색은 한 에이전트, 변경은 다른 에이전트)
  • 다중 관점 분석 (시니어 검토 + 주니어 멘토링 두 관점)

패턴 ③ Split-and-Merge — 진짜 병렬 작업

완전히 독립적인 작업들을 동시에 실행한 뒤 결과를 합친다. 토큰 비용이 3~4배지만, 작업 시간은 1/N로 줄어든다.

전형적 시나리오: "50개 파일에 같은 패턴 적용".

  파일들이 서로 독립적이니 병렬로 진행해도 좋아.
  각 파일 변경 후 빌드 확인까지.

[Claude Code]

- agent-2: ...

병렬 작업의 함정: 의존성이 있는 작업을 병렬화하면 충돌. "VendorService를 수정하면서 동시에 그것을 쓰는 OrderController도 수정"은 안 된다. 진짜 독립적인지 사전에 확인하고 시작.

패턴 ④ Agent Teams — 자율 협업

리드 에이전트가 팀 에이전트들을 조율하며 큰 프로젝트를 자율적으로 진행한다. Anthropic 공식 문서 표현: "Multiple Claude Code agents that work on different parts of a task simultaneously. A lead agent coordinates the work, assigns subtasks, and merges results."

가장 강력하지만 가장 비싸다. 4시간 짜리 기능을 45분으로 줄였다는 사례가 있는 반면, 단순 작업에 동원해 4배 토큰을 쓰고도 결과가 더 안 좋아진 사례도 흔하다.

패턴 ⑤ Headless — UI 없는 자동화

--print 플래그로 대화형 UI 없이 stdout 스트리밍 모드로 실행. CI/CD나 정기 작업에 끼워 넣는다.

Headless — CI 통합 예
# GitHub Actions의 한 step
claude --print "
  방금 머지된 PR의 diff를 보고
  CHANGELOG.md에 사용자 관점 변경사항 한 줄을 추가해.
  내부 모듈명·클래스명은 노출하지 마.
" | tee changelog-entry.txt

# 정기 점검
claude --print "
  최근 7일간 커밋된 새 SQL 쿼리들을 보고
  N+1 가능성이 있는 것만 보고서로 만들어.
" > weekly-perf-report.md

Headless 모드의 진가는 "키보드 앞에 없을 때 작동"이다. 야간 자동 검토, 정기 보고서 작성, PR 자동 라벨링, 이슈 자동 분류 등.

Headless에서 위험: 되돌릴 수 없는 작업(파일 삭제, DB 쓰기, 외부 API 발송)은 사람 검토 게이트를 사이에 둬야 한다. 의심스러우면 결과만 보고서로 만들고, 실행은 사람이 검토 후.

패턴 선택 — 의사결정 프레임

실무 권장 시작점: 모든 작업을 Sequential로 시작. 익숙해지면 CI 자동화에 Headless 추가. Operator/Agent Teams는 진짜로 독립적인 병렬 작업이 있을 때만 꺼낸다 — 토큰 비용이 3~4배다.

"MCP는 AI 도구를 외부 데이터 소스에 연결하는 오픈 표준이다. Claude Code는 MCP로 Google Drive 디자인 문서를 읽고, Jira 티켓을 업데이트하고, Slack 데이터를 끌어오고, 사내 시스템과 통합할 수 있다."Anthropic — Claude Code overview

커넥터 등록 — 데스크톱 앱 vs CLI

MCP 커넥터를 등록하는 가장 쉬운 방법은 Claude Desktop App의 GUI 설정이다. Settings → Connectors에서 클릭으로 추가한다. 한 번 추가하면 같은 계정의 Claude Code, Cowork에서도 동일하게 쓸 수 있다.

CLI 환경에서 직접 등록하려면 .mcp.json 설정 파일을 사용한다:

~/.claude/.mcp.json — 프로젝트 또는 전역 설정
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    },
    "sqlserver": {
      "command": "npx",
      "args": ["-y", "@some/mssql-mcp"],
      "env": { "MSSQL_CONN": "${ACME_DEV_CONN}" }
    }
  }
}

토큰·시크릿은 절대 파일에 직접 박지 말 것. 환경변수 참조(${VAR})만 쓰고, 변수는 OS 시크릿 매니저나 사내 비밀 보관소에서 주입. 실수로 git에 커밋되는 일이 가장 흔한 사고다.

커넥터 사용의 안전 원칙

  1. 최소 권한 — 각 커넥터는 필요한 만큼의 스코프만. GitHub은 read-only가 충분한 경우가 많다.
  2. 읽기와 쓰기 분리 — 같은 시스템도 읽기용 / 쓰기용 커넥터를 분리. 쓰기는 명시적 시점에만 활성화.
  3. 위험 작업은 사람 승인 — 메일 발송, 결제, DB 쓰기 같은 작업은 권한 모드를 Default로 두고 매번 승인.
  4. 감사 로그 — 어떤 커넥터가 언제 무엇을 호출했는지 로그에 남긴다 (Claude Code 자체 로그 + 커넥터 측 로그).
  5. 스코프별 분리 — 개인용·팀 공용·민감정보용 워크스페이스를 분리해서 커넥터별로 권한을 다르게.

자체 사내 ERP 노출 — 언제 자체 MCP 서버를 만들 가치가 있나

이 가이드는 자체 MCP 서버 구현을 다루지 않지만, 결정 시점은 짚고 가자. 다음 조건을 모두 만족할 때만 자체 서버를 만든다:

  • 같은 사내 시스템을 여러 표면(Claude Code + Desktop + 모바일)에서 쓸 계획이 있다.
  • 기존 GitHub/SQL/Filesystem 커넥터로는 노출이 불가능한 고유 비즈니스 로직이 있다 (예: AcmeERP의 "발주 가능 여부 검증").
  • 팀에 유지보수할 사람이 있다. MCP 서버는 코드다 — 만들면 돌봐야 한다.

이 셋 중 하나라도 빠지면, 일단 기존 커넥터로 80%를 해결하고 나머지는 사람이 처리하는 게 합리적이다.

실무 권장 출발점: 첫 달에는 GitHub + Jira + Notion 셋만 등록. 익숙해진 후 SQL 읽기 전용 추가. 자체 MCP는 6개월 이상 운영해 본 후 결정.

슬래시 커맨드와 서브에이전트

"팀이 같은 흐름을 공유할 때, 그 흐름을 매번 프롬프트로 다시 적지 마라. 슬래시 커맨드로 한 번 적고 모두가 쓴다."Claude Code 운영 원칙

CLAUDE.md가 "이 프로젝트는 어떤 곳인가"를 정의한다면, 슬래시 커맨드와 서브에이전트는 "이 프로젝트에서 어떻게 일하는가"를 정의한다. 둘 다 git에 커밋되는 마크다운 파일이다.

슬래시 커맨드 — 재사용 가능한 워크플로우

자주 쓰는 워크플로우(예: PR 리뷰, 릴리즈 노트 작성, 마이그레이션 추가)를 .claude/commands/ 아래에 마크다운 파일로 저장하면 슬래시 커맨드로 호출할 수 있다.

.claude/commands/review-pr.md
---
description: 현재 브랜치의 PR을 보안 + 성능 + 스타일 관점에서 검토
---

다음 순서로 작업해라:

1. `git diff main...HEAD` 로 현재 변경사항을 본다.
2. 다음 세 관점에서 각각 분리된 섹션으로 검토 결과를 작성:

   ## 보안 검토
   - SQL injection, 권한 누락, 비밀 노출 가능성만 본다.
   - 발견 없으면 "이슈 없음"이라고 명시.

   ## 성능 검토
   - N+1 쿼리, 동기 차단, 큰 allocation을 찾는다.
   - 추측은 하지 마라. 코드의 실제 패턴만 인용.

   ## 스타일 검토
   - CLAUDE.md의 코딩 규칙을 위반한 부분만 본다.
   - 단순 취향 차이는 언급하지 않는다.

3. 마지막에 "Block / Comment / Approve" 중 하나로 종합 의견.

이제 팀의 모든 사람이 한 줄로 이 워크플로우를 호출할 수 있다:

Terminal — Slash command 사용
> /review-pr

[Claude Code: 정의된 흐름대로 진행]
## 보안 검토
- VendorService.cs:127 — 사용자 입력을 LIKE 절에 직접 사용. injection 위험.
...
## 성능 검토
- 이슈 없음.
## 스타일 검토
- VendorRepository.cs:45 — async 메서드인데 Async 접미사 누락 (CLAUDE.md 규칙).

종합: Block — 보안 이슈 1건 수정 필요

슬래시 커맨드의 위치

위치스코프용도
~/.claude/commands/전역개인 자주 쓰는 흐름
.claude/commands/ (프로젝트)팀 공통git 커밋, 모두가 공유

실무에서 자주 쓰는 슬래시 커맨드 5가지

  • /review-pr — 위에서 본 형태. 머지 전 자체 검토.
  • /add-migration — 새 DB 마이그레이션 + rollback 스크립트 표준 양식 생성.
  • /release-notes — 최근 머지된 PR들로 사용자 관점 변경사항 작성.
  • /explain — 특정 모듈을 신입에게 설명하듯이 요약 (온보딩용).
  • /fix-flaky — 불안정한 테스트를 특정해 안정화.

서브에이전트 — 역할이 명확한 보조

슬래시 커맨드가 "이 흐름으로 작업해"라면, 서브에이전트는 "이 역할로 작업해"다. .claude/agents/ 아래에 마크다운 파일로 정의한다.

.claude/agents/security-reviewer.md
---
name: security-reviewer
description: 코드의 보안 이슈만 검토한다. SQL injection, XSS, 권한 누락, 비밀 노출.
tools: Read, Glob, Grep
model: sonnet
---

당신은 보수적인 보안 감사관이다.

원칙:
- 보안 이슈 외에는 절대 언급하지 마라. 스타일·성능은 다른 에이전트의 일.
- 의심스러우면 위험을 더 높게 표시한다.
- 발견할 때마다 정확한 파일·라인 번호와 위반된 보안 원칙을 함께 적는다.
- 입증되지 않은 추측은 "potential" 표시. 확인된 것은 "confirmed".

출력 형식:
- severity: critical | high | medium | low
- file:line
- description: 1-2 문장
- recommendation: 구체적 수정 방향

YAML frontmatter의 의미:

  • name — 호출 시 사용할 이름
  • description — 자동 매칭에 쓰임. Claude Code가 이 description을 보고 작업이 일치할 때 자동 호출
  • tools — 이 에이전트가 쓸 수 있는 도구 한정 (보안 리뷰어에게 Edit 권한을 주지 않는 이유)
  • model — 모델 선택. 단순 작업이면 Haiku로 비용 절감

자동 매칭 — Claude Code가 알아서 부른다

서브에이전트의 진가는 자동 위임에 있다. 사용자가 "이 코드의 보안 점검해줘"라고 하면, Claude Code가 security-reviewer의 description을 보고 자동으로 위임한다 — 명시적으로 부르지 않아도.

이게 잘 작동하려면 description 필드를 모델이 결정에 쓸 수 있게 적어야 한다:

나쁜 description

"보안 일을 한다"

좋은 description

"코드의 보안 이슈만 검토한다. SQL injection, XSS, 권한 누락, 비밀 노출."

자주 쓰는 서브에이전트 패턴 4가지

  • code-reviewer — 일반 품질 검토. Read·Grep만 허용해 변경 못 하게.
  • security-reviewer — 위 예시.
  • test-writer — 새 테스트 작성 전담. Edit 허용.
  • doc-writer — 코드 변경에 따른 문서 업데이트.

훅(hooks) — 자동 검증과 강제

서브에이전트가 호출되는 자동화라면, 훅은 이벤트에 반응하는 자동화다. .claude/hooks/에 정의하며, 파일 편집 후 자동 린트, 커밋 전 테스트 실행 등을 시킬 수 있다.

훅의 진가는 "잊을 수 없는 검증"이다. 사람은 잊어도 훅은 잊지 않는다. CI 게이트와 비슷하지만 더 빠른 피드백 루프 — 머지 전 PR이 아니라 편집 직후에 동작한다.

훅의 절제: 모든 편집마다 무거운 작업을 돌리면 작업 흐름이 느려진다. 진짜 중요한 검증(린트·기본 빌드)만 훅으로, 풀 테스트 스위트는 CI에 맡긴다.

  5. 고객문의 1차 분류 — 들어오는 문의를 부서·우선순위로 라우팅

// src/Vendors/Models/VendorClassificationInput.cs
namespace AcmeErp.Vendors.Models;

/// <summary>
/// 거래처 자동 분류기에 입력되는 비정형 거래처 정보.
/// </summary>
public record VendorClassificationInput(
    string CompanyName,
    string? FreeFormMemo,
    string? AttachmentText);

// src/Vendors/Models/VendorClassificationResult.cs
namespace AcmeErp.Vendors.Models;

public record VendorClassificationResult(
    string IndustryCode,
    string TransactionType,
    string CreditTier,
    double Confidence,
    bool NeedsReview,
    string[] Reasoning)
{
    public static readonly string[] ValidIndustryCodes =
    [
        "MFG-AUTO", "MFG-CHEM",
        "TRD-RETAIL", "TRD-WHOLESALE",
        "SVC-IT", "SVC-LOGI",
        "OTHER"
    ];

    /// <summary>화이트리스트 위반 시 OTHER로 정규화.</summary>
    public VendorClassificationResult Normalize() =>
        ValidIndustryCodes.Contains(IndustryCode)
            ? this
            : this with {
                IndustryCode = "OTHER",
                NeedsReview = true,
                Reasoning = [..Reasoning, "unknown industry, normalized to OTHER"]
              };
}

// src/Vendors/Classification/IVendorClassifier.cs
namespace AcmeErp.Vendors.Classification;

public interface IVendorClassifier
{
    Task<VendorClassificationResult> ClassifyAsync(
        VendorClassificationInput input,
        CancellationToken ct = default);
}

이 흐름의 핵심 가치

  • 사용자는 단 한 줄도 .cs 코드를 직접 적지 않았다. 의도·검토·승인만 했다.

목표 시나리오

시나리오

영업사원이 받는 RFQ(견적 요청) 메일을, 견적서 1차 드래프트로 자동 변환하는 워크플로우를 구현한다. 메일에서 발주 항목을 추출하고, AcmeERP의 단가표와 매칭하고, 표준 양식의 견적서 초안을 만든다. 최종 발송은 절대 자동으로 하지 않는다 — 영업 담당자가 검토하고 직접 발송한다.

왜 이 시나리오가 다른가

Chapter 15(거래처 분류기)는 독립된 기능을 처음부터 만드는 작업이었다. 이번은 여러 단계가 사슬처럼 이어지고, 그 중간에 사람 게이트가 들어가는 워크플로우다.

Part 2 Chapter 4에서 본 Prompt Chaining 패턴(Explore-Plan-Implement-Verify의 일반형)이 그대로 적용된다 — 단, 단계 사이에 사람 승인 게이트가 끼어든다.

2단계 — 검토 + 노트, 핵심은 게이트의 강도

이 시나리오에서 가장 중요한 검토 포인트는 "발송 자동화의 강도"다. 사람 검토가 형식적이면 환각 가격이 그대로 고객에게 발송될 위험이 있다.

검토 노트 — 안전 게이트 강화
> 노트 반영해. 아직 구현은 하지 마.

  1. 입력은 텍스트 페이스트만 우선 (이메일 첨부 파싱은 다음 PR)
  2. 단가표 뷰: vendor_price_v (이미 존재). 컬럼: item_code,
     vendor_id, unit_price, valid_from, valid_to
  3. 만료일: 견적서 발행일로부터 30일
  4. 사람 게이트를 두 단계로 강화:
     - approve 시: 영업 담당자 + 단가가 표준에서 ±10% 벗어나면
       팀장 승인까지 필요 (이중 게이트)
     - send 시: 추가 클릭 + 발송 직전에 단가 변경 여부 재검증
  5. 모든 LLM 호출 결과는 reasoning[] 필드로 어떤 추출 근거가
     있었는지 함께 저장 — 사후 감사용
  6. 단가 매칭 실패율이 30% 넘으면 알람 (단가표 누락 신호)
  7. needs_review 항목이 1개 이상이면 자동 승인 절대 불가
     (UI에서 승인 버튼 비활성화)

이 노트들은 Chapter 5(환각 최소화)의 패턴이 모두 녹아 있다 — 출력 검증 게이트, 사람 승인, 외부 사실 확인(가격 재검증), 근거 인용 강제(reasoning[]).

4단계 — 사람 게이트 UI

견적서 초안이 만들어지면 영업 담당자에게 보여준다. 이 부분은 ERP의 기존 UI 패턴을 그대로 쓰지만, 다음 가드가 필수:

  • needs_review 항목은 빨간색으로 표시 — 시각적으로 숨길 수 없게.
  • 승인 버튼은 needs_review가 0일 때만 활성화.
  • 단가가 표준 ±10% 벗어나면 승인 시 팀장 승인 단계 추가.
  • 발송 버튼은 별도 화면에서, 한 번 더 확인.
  • 발송 직전 단가 재검증 — 초안 작성 후 단가표가 바뀌었을 수 있음.

핵심 원칙: "되돌릴 수 없는 작업"(메일 발송, 결제, DB 쓰기)은 도구가 직접 실행하지 않는다. 항상 데이터로만 만들고 사람이 명시적 클릭으로 실행. 이게 LLM 워크플로우의 가장 중요한 안전 원칙이다.

두 시나리오의 공통 교훈

Chapter 15와 16에서 본 두 시나리오는 다른 일처럼 보이지만 같은 원칙을 따른다:

  1. Plan Mode로 시작 — 큰 작업은 한 시간의 사전 투자가 6시간을 절약한다.
  2. "don't implement yet" 가드 — 합의 없이는 구현 시작 안 함.
  3. CLAUDE.md가 기반 — 프로젝트 규칙·금지사항이 모든 결정에 자동 적용.
  4. 테스트를 먼저 — 명세 역할 + 자동 검증.
  5. 서브에이전트로 자체 리뷰 — Operator 패턴으로 자기평가 편향 우회.
  6. 되돌릴 수 없는 작업에 사람 게이트 — 도구가 자동 실행하지 않는다.
  7. 운영 후 모니터링 — Headless 정기 작업으로 품질 추적.

이 7가지가 ERP 도메인을 넘어 거의 모든 LLM 통합에 적용된다. 다른 시나리오(재고 봇, 사내 규정 RAG, 고객문의 분류)도 결국 같은 골격이다.

Cowork란 무엇인가

Claude Desktop App의 모드 중 하나. 로컬 파일 시스템에 권한을 주고 Claude가 자율적으로 다단계 업무를 수행한다. 채팅과는 다르다 — Claude가 컴퓨터에서 실제로 파일을 만들고, 코드를 돌리고, 결과물을 폴더에 떨어뜨린다.

Anthropic 공식 표현: "채팅처럼 주고받는 느낌이 아니라, 동료에게 메시지를 남기고 결과를 받는 느낌."

접근 조건

  • Claude Desktop App 필수 (macOS / Windows). 웹·모바일 단독으로는 불가능.
  • 유료 플랜 필요 (Pro / Max / Team / Enterprise).
  • 모드 전환: 데스크톱 앱에서 Chat ↔ Cowork 탭으로 전환.
  • 앱이 켜져 있어야 작동. 닫으면 작업이 멈춘다 (정기 작업 포함).

ERP 개발자에게 유용한 Cowork 활용 4가지

① 발주서·계약서 일괄 처리

거래처에서 받은 PDF 발주서들을 폴더에 모아두고, Cowork에게 다음을 시킨다:

~/Documents/Inbox 폴더의 모든 PDF를 읽어서 다음을 해줘:
- 거래처명, 자재코드, 수량, 단가를 추출
- 결과를 orders-extracted.xlsx로 저장 (시트별로 거래처)
- 단가가 표준에서 ±10% 벗어난 항목은 빨간색 강조
- 추출 실패한 PDF는 _needs_review 폴더로 이동
- 처리 결과 요약을 summary-{날짜}.md로 저장

이 작업은 사람이 몇 시간 걸린다. Cowork는 같은 일을 30분에 끝낸다. 관건은 마지막에 사람이 검토하는 단계가 워크플로우에 명시적으로 들어가야 한다는 것이다.

② 정기 보고서 자동화

매주 월요일 오전 9시에 /schedule 커맨드로 정기 작업을 등록할 수 있다:

/schedule weekly Monday 9am

매주 월요일 오전 9시에:
- ~/Reports 폴더의 지난 주 데이터 파일들을 읽어
- 표준 양식의 주간 영업 리포트를 생성 (template.pptx 기반)
- ~/Reports/Weekly/{date}.pptx로 저장
- 요약 한 단락을 메일 초안으로 ~/Reports/Weekly/{date}-email.md에

주의: 앱이 켜져 있어야 정기 작업이 돈다. 노트북이 잠자기에 들어가면 멈춘다. 진짜 무인 자동화가 필요하면 서버 환경(Headless Claude Code 또는 별도 자동화 인프라)을 쓰는 게 맞다.

③ 폴더 정리·파일 일괄 작업

개발자도 흩어진 다운로드, 아카이브 폴더 정리에 시간을 쓴다. Cowork는 이런 단순 반복을 자연어로 시킬 수 있다.

~/Downloads에서:
- 같은 내용 중복 파일 식별 (파일명 + 내용 해시)
- 중복은 _duplicates 폴더로 (가장 최신만 남기고)
- 나머지는 종류별로 분류 (Documents/Images/Installers)
- 마지막에 정리 요약 보여줘

④ 사양서·표준문서 동기화

코드와 문서가 어긋나면 곤란하다. Cowork에게 정기적으로 동기화 검사를 시킨다:

~/Projects/AcmeERP/docs와 ~/Projects/AcmeERP/src를 비교해서:
- src의 public API가 변경됐는데 docs가 업데이트 안 된 부분 찾기
- 결과를 docs-drift-{date}.md로 저장
- 각 항목에 어떤 문서를 어떻게 고쳐야 하는지 제안만

전역 지침과 폴더별 지침

Claude Code의 CLAUDE.md에 해당하는 Cowork의 영구 지침이다.

  • Global Instructions (Settings → Cowork → Global instructions) — 모든 Cowork 작업에 적용.
  • Folder Instructions — 특정 폴더 선택 시에만 적용. Claude가 작업 중 자동 업데이트할 수도 있다.

실무 권장 Global Instructions 예시:

당신은 내 작업 보조다.

작업 시작 전:
- 목표·산출 형식·청자가 모호하면 먼저 질문해라. 추측해서 시작하지 마라.

작업 중:
- 사실·날짜·숫자·승인은 만들어내지 마라. 모르면 unknown 또는 needs_review.
- 중요한 결정 시점에는 멈추고 확인 요청.
- 산출물은 항상 별도 파일로 저장 (이름은 작업 내용을 반영하게).

작업 후:
- 무엇을 했고 무엇을 못했는지 한 단락 요약.
- 사람이 검토해야 할 항목은 명시적으로 표시.

Cowork의 한계 — 솔직히 알아두기

Cowork는 만능이 아니다. 다음은 실무에서 보고되는 한계다:

  • 데스크톱 앱 의존 — 앱이 켜져 있어야 작동. 진짜 무인 백그라운드 실행은 불가.
  • 로컬 머신 자원 사용 — 작업 중에 노트북이 느려진다.
  • 큰 스프레드시트 한계 — 수만 행짜리 xlsx 파싱이 가끔 실패.
  • 되돌릴 수 없는 작업의 위험 — 폴더 정리하다 잘못 삭제하면 복구 어려움. 중요한 데이터는 백업하고 시키기.
  • 운영 자동화엔 부적합 — ERP 야간 배치 같은 production 자동화는 Cowork가 아닌 서버 인프라로.

가장 흔한 함정: Cowork에 너무 넓은 폴더 권한을 주는 것. 항상 작업 전용 폴더를 만들어 거기만 권한 주고, 민감한 데이터는 별도 분리. 데스크톱 전체 접근 권한은 절대 안 된다.

Cowork와 Claude Code의 협업 시나리오

두 도구는 경쟁이 아니라 역할 분담이다. AcmeERP 개발자의 하루를 예로 들면:

  • 오전: Claude Code로 ACME-1234 티켓 구현 (Plan Mode → Sequential).
  • 오후: Claude Code로 코드 리뷰·테스트 보강 후 PR 생성.
  • 퇴근 전: Cowork에 "내일 아침 회의 자료 — 이번 주 처리한 거래처 등록 50건의 분류 정확도 분석" 시켜놓고 퇴근.
  • 다음 날 출근: 분석 결과 .pptx가 데스크톱에 준비됨.

이 패턴이 자리 잡으면 두 도구가 자연스럽게 보완한다 — 개발 작업은 Claude Code, 분석·문서·정리는 Cowork.

실무 권장 출발점: Claude Code부터 익히고(2~4주), Cowork는 정기 업무 중 단순 반복이 보일 때 추가. 두 도구를 동시에 도입하면 어느 쪽도 깊이 익히기 어렵다. "코드는 Code, 그 외는 Cowork"의 분업이 가장 자연스럽다.

## What this project is
{한 단락으로 — 어떤 회사의 어떤 시스템인지, 규모(거래처 수, 일일 트랜잭션 수)}

- Logging: {Serilog / NLog}
- DI: Microsoft.Extensions.DependencyInjection
- API: ASP.NET Core (REST)

## Coding rules
- public API에는 XML doc 주석 필수
- 비동기 메서드는 항상 `Async` 접미사

- 새 마이그레이션 시 rollback 스크립트 동반
- {팀 고유 규칙 추가}

- {중요한 결정 3~5개. 왜 그렇게 정했는지 한 줄씩.}

- 거래처 정보 추측·자동완성 금지. 명시 안 되면 needs_review.

- LLM 호출 비용·시간을 고려해 동기 응답 흐름에는 LLM 넣지 마라
  (반드시 비동기 워커로 분리).
- {팀의 학습된 금지사항 추가}

A.2

슬래시 커맨드 모음 — 즉시 사용

모두 .claude/commands/ 아래에 마크다운 파일로 저장하면 된다.

/review-pr — 자체 PR 리뷰

---
description: 현재 브랜치 변경사항을 보안+성능+스타일로 분리해 리뷰
---

다음 순서로 작업:

1. `git diff main...HEAD`로 변경사항 확보.
2. 다음 세 섹션으로 분리해 리뷰:

   ## 보안
   - SQL injection, 권한 누락, 비밀 노출만.
   - 발견 없으면 "이슈 없음" 명시.

   ## 성능
   - N+1, 동기 차단, 큰 allocation만.
   - 측정 없이 "이거 느릴 것 같다"는 추측 금지.

   ## 스타일
   - CLAUDE.md 규칙 위반만 지적.
   - 단순 취향 차이는 언급 안 함.

3. 마지막에 종합 의견: "Block | Comment | Approve".

/add-migration — DB 마이그레이션 추가

---
description: 표준 양식의 SQL 마이그레이션 + rollback 자동 생성
arguments: ticket, description
---

티켓 번호 {ticket}와 설명 "{description}"을 받아서:

1. 다음 두 파일을 생성:
   - migrations/{YYYYMMDD}_{ticket}_{snake_case_desc}.sql
   - migrations/rollback/{YYYYMMDD}_{ticket}_rollback.sql

2. 마이그레이션 파일 표준 양식:
   - 헤더 주석에 티켓 번호·작성일·작성자
   - IF NOT EXISTS 체크 포함
   - 트랜잭션 BEGIN/COMMIT 감싸기
   - 영향 받는 인덱스 검토 코멘트

3. rollback 파일도 같은 표준.

4. 마이그레이션 검증 명령 실행:
   `dotnet run --project tools/MigrationRunner -- --validate-only`

5. 변경 요약을 한 단락으로 출력.

/release-notes — 사용자 관점 릴리즈 노트

---
description: 최근 머지된 PR들로 사용자 관점 변경사항 한 단락씩 작성
---

1. 최근 1주일간 main에 머지된 PR 목록 확인.
2. 각 PR마다:
   - title + description 읽기
   - 사용자 관점 변경사항 한 문장 작성
   - 카테고리: [기능 추가 | 개선 | 버그 수정 | 보안]
   - 내부 모듈명·클래스명 노출 금지
   - 원인·기술적 배경 노출 금지
3. 결과를 release-notes-{날짜}.md로 저장.

/explain — 모듈 온보딩 설명

---
description: 특정 모듈을 신입 개발자에게 설명하는 형태로 요약
arguments: module_path
---

{module_path} 디렉토리를 읽고 다음 구조의 문서 작성:

1. 한 단락 — 이 모듈이 뭐 하는 곳인가
2. 핵심 클래스 3~5개 — 각 100자 이내 설명
3. 주의할 점 — CLAUDE.md 규칙 중 이 모듈에 특히 적용되는 것
4. 첫 작업 추천 — 신입이 처음 만져볼 만한 작은 작업 제안

코드 발췌 금지. 설명만.
